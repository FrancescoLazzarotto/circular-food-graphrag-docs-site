    Ambiente Python¶

    ambiente tipo a cosa serve dove sta oggi
    graphllm conda, Python 3.12.13 tutto il codice della repo: CLI, pipeline del grafo, valutazione, demo, test /mnt/storage/<utente>/.conda/envs/graphllm
    vllm-serve venv, Python 3.12.13, vLLM 0.19.1 solo per servire i modelli (generatore ed encoder) con gli script scripts/serving/start_vllm*.sh /mnt/storage/<utente>/venvs/vllm-serve
    neo4jrt conda fornisce Java (OpenJDK 21.0.10) al database Neo4j /mnt/storage/<utente>/.conda/envs/neo4jrt
    ontology venv, Python 3.12.13, rdflib 7.6.0, pyshacl 0.40.1, skosify 2.3.0 gli script di ontology/scripts/ che costruiscono e controllano l'ontologia dei quadri; si crea con i due comandi di ontology/README.md:91-92 /mnt/storage/<utente>/venvs/ontology

    graphllm: l'ambiente del codice¶

    Usarlo¶

    conda activate graphllm
export PYTHONNOUSERSITE=1      # vedi "Il site-packages dell'utente" più sotto
cd /srv/projects/graphllm/experiments/graphRAGPipelineExp1

    Negli script conviene conda run -n graphllm python …, così il comando non dipende dalla shell da cui parte.

    Crearne uno nuovo¶

    conda create -n graphllm python=3.12 -y
conda activate graphllm
cd /srv/projects/graphllm/experiments/graphRAGPipelineExp1
pip install -e ".[demo,eval,dev]"
    • pip install -e . installa il pacchetto graphrag-pipeline 0.2.0 in modo modificabile: il codice resta quello della cartella della repo, non una copia (pyproject.toml:6-7). Python minimo dichiarato: 3.10 (pyproject.toml:10).
    • Gli extra si aggiungono tra parentesi quadre (pyproject.toml:49-78):
    extra cosa aggiunge
    demo Streamlit, per la demo nel browser
    eval RAGAS, pandas, datasets, ROUGE, matplotlib, numpy
    gpu bitsandbytes, autoawq, vllm (non serve qui: i modelli si servono da vllm-serve)
    dev pytest, pytest-cov, ruff
    • L'installazione crea tre comandi (pyproject.toml:80-83): graphrag-demo (= python -m graphrag.cli), graphrag-eval (valutazione) e graphrag-kg (pipeline del grafo).
    • Per risultati confrontabili con i run già fatti la repo fornisce requirements.lock, con le versioni esatte dell'ambiente in cui sono state prodotte le misure: pip install -r requirements.lock.
    • In alternativa si può ricreare l'ambiente di oggi da env_snapshots/graphllm.conda-export.yml, esportato con conda env export --no-builds. Prima va tolta la riga graphrag-pipeline==0.2.0, che non esiste su PyPI; poi si fa pip install -e . dalla repo. Nel file c'è anche il campo prefix: con il percorso di Francesco: va cambiato o tolto.

    Il site-packages dell'utente¶

    Se un utente ha installato pacchetti con pip install --user, quei pacchetti stanno in ~/.local/lib/python3.12/site-packages e hanno la precedenza su quelli dell'ambiente conda. Nell'utente <utente> ce ne sono 146 (277 voci nella cartella, contando i moduli), con versioni incompatibili.

    Misurato nell'ambiente graphllm:

    pacchetto senza PYTHONNOUSERSITE (vince ~/.local) con PYTHONNOUSERSITE=1 (ambiente conda)
    torch 2.5.1+cu124 2.10.0
    sentence-transformers 5.3.0 3.4.1
    graphrag-pipeline 0.1.0 0.2.0

    Il miscuglio rompe la demo all'avvio con ModuleNotFoundError: Could not import module 'PreTrainedModel'. Per questo start_demo.sh esporta PYTHONNOUSERSITE=1 (scripts/serving/start_demo.sh:24-31). Fuori da quello script bisogna esportarlo a mano. Chi crea un proprio utente e un proprio ambiente non ha questo problema, finché non usa pip install --user.

    Lo stesso vale per il comando pip: con conda run -n graphllm, which pip dà ~/.local/bin/pip, non il pip dell'ambiente, e un conda run -n graphllm pip install … non installa nell'ambiente. Per installare un pacchetto in graphllm si usa il Python dell'ambiente: /mnt/storage/<utente>/.conda/envs/graphllm/bin/python -m pip install <pacchetto>. pyoxigraph 0.5.13, che serve a scripts/kg/quality/graph_rdf_export.py per rileggere l'esportazione RDF, è installato così; non è fra le dipendenze di pyproject.toml.

    vllm-serve: l'ambiente dei modelli¶

    import vllm non funziona dentro graphllm (AGENTS.md:170); per questo i modelli si servono da un ambiente a parte. Ogni script scripts/serving/start_vllm*.sh lo usa tramite la variabile VLLM_BIN, che di default vale /mnt/storage/<utente>/venvs/vllm-serve/bin/vllm (per esempio start_vllm_qwen38_27b.sh:25). Per usare un altro ambiente basta esportare VLLM_BIN prima di lanciare lo script.

    Nella repo non c'è una ricetta per crearlo. L'elenco esatto dei pacchetti di oggi è in env_snapshots/vllm-serve.pip-freeze.txt: vLLM 0.19.1, torch 2.10.0, FlashInfer 0.6.6, transformers 5.13.0.

    I pesi dei modelli non stanno nell'ambiente ma nella cache condivisa di Hugging Face /mnt/storage/hf-cache (222 GB con du -sh, gruppo llmproject), che gli script usano come HF_HOME predefinito (per esempio start_vllm_qwen38_27b.sh:27). Ogni script start_vllm*.sh scrive export HF_HOME="${HF_HOME:-/mnt/storage/hf-cache}", quindi una HF_HOME già esportata vince; come cambiare cartella dei pesi: Servire i modelli.

    neo4jrt: Java per il grafo¶

    Serve solo al database. Il percorso è scritto come JAVA_HOME nel file delle impostazioni del grafo (~/.config/graphrag/graph-db.env), che deploy/graph/install.sh crea. I dettagli stanno in Server e servizi.

    Variabili d'ambiente e file .env¶

    Il codice legge credenziali e indirizzi dalle variabili d'ambiente. I file .env le riempiono, ma ogni punto d'ingresso li carica in modo diverso, e la differenza decide a quale grafo ci si collega.

    punto d'ingresso quale file chi vince se una variabile è già esportata ancora
    python -m graphrag.cli il primo .env trovato risalendo dalla cartella di cli.py, cioè .env alla radice della repo la variabile esportata src/graphrag/cli.py:1229 (load_dotenv(override=False))
    scripts/smoke/smoke_check.py --env-file (default kg_pipeline/.env), poi il .env alla radice la variabile esportata smoke_check.py:212-216, 264-265
    product/app.py, product/console.py DEMO_ENV_FILE (default kg_pipeline/.env) la variabile esportata product/config.py:404, 447
    python -m kg_pipeline.main --env-file (default kg_pipeline/.env) il file kg_pipeline/main.py:810, 837 (override=True)

    Il modo in cui load_dotenv() senza argomenti trova il file è quello di python-dotenv 1.2.2, installato in graphllm: risale le cartelle partendo da quella del file che lo chiama.

    Verificare che l'ambiente funzioni¶

    python scripts/smoke/smoke_check.py --check-imports-only

    Controlla solo che torch, langgraph, transformers e neo4j si importino (smoke_check.py:267-282). Output, in 3 secondi:

    IMPORT CHECK PASSED

    Il controllo completo verifica anche il grafo (nodi presenti e indici node_search e node_embedding attivi), il generatore e l'encoder (smoke_check.py:34, 295-318). Fa solo letture: query di lettura sul grafo e una richiesta GET /models ai server dei modelli. In una shell nuova fallisce, per i due motivi spiegati sopra. Output, senza aver caricato le impostazioni del grafo:

    FAILED neo4j: no usable graph. primary: Cannot resolve address 588fe1bc.databases.neo4j.io:7687. fallback: Couldn't connect to localhost:7689 ...
FAILED llm: generator: http://localhost:8000/v1 unreachable (<urlopen error [Errno 111] Connection refused>)
FAILED encoder: encoder: http://localhost:8002/v1 unreachable (<urlopen error [Errno 111] Connection refused>)
SMOKE CHECK FAILED

    Cosa dice ogni riga:

    • neo4j: il grafo principale è Aura, irraggiungibile; il ripiego (DEMO_NEO4J_FALLBACK_URL in kg_pipeline/.env) è il grafo di staging su :7689, spento quando non serve. Il grafo di produzione su :7687 non viene neppure provato.
    • llm: il generatore viene cercato all'indirizzo di VLLM_BASE_URL in kg_pipeline/.env, cioè :8000, la porta dell'estrattore usato per costruire il grafo (smoke_check.py:192-200). Il generatore della demo sta su :8001. Quel giorno non girava nessun modello.
    • encoder: :8002, spento quel giorno.

    Con le impostazioni di produzione caricate, e saltando i due modelli spenti:

    set -a; source ~/.config/graphrag/graph-db.env; set +a
python scripts/smoke/smoke_check.py --skip-llm --skip-encoder

    OK     neo4j: primary bolt://localhost:7687 — 23250 nodes (+23250 :NodeVec carriers), indexes online
SKIPPED llm (waived on the command line)
SKIPPED encoder (waived on the command line)
SMOKE CHECK PASSED

    La riga del grafo conta a parte i nodi del grafo e i nodi :NodeVec che portano i vettori, uno per nodo, perché contati insieme darebbero il doppio (smoke_check.py:63-68, 88). La riga del grafo viene dal controllo con le NEO4J_* del grafo di produzione (lì anche con generatore ed encoder controllati). I 46.500 nodi contati insieme sono 23.250 nodi del grafo più 23.250 portatori (vedi Il grafo di produzione).

    Con i modelli accesi, per controllare il generatore della demo invece dell'estrattore si passa la sua porta: --llm-base-url http://localhost:8001/v1 (smoke_check.py:227-239). Come accendere i modelli: Servire i modelli.
