    Lanciare una campagna¶

    Quando serve¶

    Una campagna è un insieme di domande (nei driver della repo le 30 del gold set, le domande di riferimento con le risposte attese: run_gold_variant.sh:4) fatte al sistema con una o più strategie di recupero, salvando su file ogni risposta con tutto quello che è stato recuperato. È il punto di partenza per ogni numero: dopo si passa a Valutare un run.

    Per confrontare il recupero "solo testo" (Standard RAG) con quello sul grafo misurando anche memoria e tempi, serve invece la Matrice di retrieval: è un altro runner, che non espone le stesse opzioni.

    Cosa tocca¶

    risorsa effetto
    modelli generatore (default dei driver: RedHatAI/Qwen3.8-27B-INT4 su :8001) ed encoder su :8002, entrambi già accesi
    GPU quella dei modelli (GPU 1); il processo della campagna non carica modelli
    grafo legge il grafo esportato nelle variabili NEO4J_*; run_gold_variant.sh usa lo staging su :7689
    disco una cartella per run, circa 7,6 MB per 240 risposte (misurato su un run)
    tempo 30 domande × 8 strategie ≈ 37 minuti con Qwen/Qwen2.5-32B-Instruct-AWQ (un run; somma delle latenze medie di un run reale; vedi sotto)

    Prima di iniziare¶

    I driver fanno questi controlli da soli e si fermano se uno fallisce. A mano:

    cd /srv/projects/graphllm/experiments/graphRAGPipelineExp1
set -a; source ~/.config/graphrag/graph-db.env; set +a     # o il grafo che si vuole misurare
curl -sf --max-time 10 http://localhost:8001/v1/models     # generatore
curl -sf --max-time 10 http://localhost:8002/v1/models     # encoder
conda run -n graphllm python scripts/kg/check_vector_index.py --min-resolving 1000

    check_vector_index.py è indispensabile: se l'indice vettoriale non punta più al grafo, il canale vettoriale tace e la campagna sembra completa ma misura un'altra cosa (commento in run_abstention_arms.sh:33-37). Vedi Avviare e fermare la demo.

    Con un driver (consigliato)¶

    I tre driver in scripts/runners/ contengono già il blocco di opzioni delle campagne di riferimento, fanno i controlli e scrivono fuori dalla repo, in /srv/projects/graphllm/experiments/exp_results_*.

    driver cosa misura grafo dove scrive (default di OUT_ROOT)
    VARIANT=<nome> bash scripts/runners/run_gold_variant.sh una variante del grafo, con le altre condizioni fisse staging, bolt://localhost:7689 (:31-34) exp_results_kg_v2/<nome>/
    bash scripts/runners/run_abstention_arms.sh tre bracci sul comportamento di astensione: A0 vecchia frase finale del prompt, A1 frase corretta, A2 frase corretta più controllo di dominio (:9-12) quello esportato exp_results_abstention/{a0_legacy_prompt,a1_repaired_prompt,a2_repaired_plus_gate}/
    bash scripts/runners/run_italian_arm.sh le stesse 30 domande in italiano (gold_v3_it.json); il suo controllo è il braccio A1, quindi va lanciato dopo gli altri bracci, nella stessa sessione del server (:11-13) quello esportato exp_results_crosslingual/it_questions/

    Ogni driver si lancia staccato dal terminale, perché dura decine di minuti:

    setsid nohup bash scripts/runners/run_abstention_arms.sh > logs/abstention_arms.log 2>&1 &
tail -f logs/abstention_arms.log

    Variabili che i driver leggono (run_gold_variant.sh:20-34; gli altri due ne leggono un sottoinsieme):

    variabile default effetto
    VARIANT obbligatoria (solo run_gold_variant.sh) nome della cartella e del tag
    OUT_ROOT /srv/projects/graphllm/experiments/exp_results_… dove scrivere
    MODEL RedHatAI/Qwen3.8-27B-INT4 --model-id
    BASE_URL http://localhost:8001/v1 --vllm-base-url
    GOLD evaluation/gold/gold_v3.json domande (GOLD_IT per il braccio italiano)
    STRATEGIES le 8 strategie solo run_gold_variant.sh lo legge dall'ambiente
    EVIDENCE_CAP 30 --evidence-max-triple-items
    EXTRA_ARGS vuota opzioni aggiuntive del CLI (solo run_gold_variant.sh)
    STAGING_URL, STAGING_USER, STAGING_PASSWORD, STAGING_DB lo staging su :7689 il grafo misurato da run_gold_variant.sh

    A mano¶

    Lo stesso blocco dei driver (run_abstention_arms.sh:46-57), braccio A1:

    conda run --no-capture-output -n graphllm python -m graphrag.cli --experiment \
  --questions-file evaluation/gold/gold_v3.json \
  --strategies "default,hybrid,text_only,no_retrieval,text_plus_triples,neighbors_focus,subgraph_2hop,shortest_path" \
  --llm --vllm --vllm-base-url http://localhost:8001/v1 \
  --model-id RedHatAI/Qwen3.8-27B-INT4 \
  --profile thesis_campaign \
  --max-new-tokens 1024 \
  --text-docs-dir artifacts/corpus_circular22 \
  --evidence-max-triple-items 30 \
  --output-dir /srv/projects/graphllm/experiments/exp_results_<famiglia>/<braccio> \
  --experiment-tag <tag>
    • --profile thesis_campaign accende le opzioni delle campagne: citazioni con etichetta, lingua forzata, risposta mirata, definizioni testuali, canale vettoriale, ancoraggio sui nodi recuperati con 3 punti di partenza, MMR (scelta dei passi di testo che evita quelli quasi uguali fra loro) con al massimo 2 passi di testo per documento (profiles.py:27-47). Un'opzione scritta esplicitamente vince sul profilo.
    • --text-docs-dir artifacts/corpus_circular22 indicizza i 22 PDF di quella cartella per il canale testuale, invece dei documenti delle esecuzioni della pipeline.
    • Il canale testuale è tfidf (lessicale), il default del CLI (cli.py:339-344): né il profilo né i driver lo cambiano. La demo usa dense. Per misurare quello che usa la demo si aggiunge --text-retriever-backend dense (COMMANDS.md, sezione 7).
    • --legacy-insufficiency-wording ripristina la vecchia frase finale del prompt usata nelle campagne E1-E8 (cli.py, aiuto dell'opzione).

    Un solo cambiamento per braccio. Due bracci si confrontano solo se differiscono in una cosa; tutto il resto del blocco deve restare identico.

    Formati del file di domande¶

    --questions-file sceglie il formato dall'estensione (cli.py:916-990):

    estensione formato
    .json la forma del gold: {"queries": [{"query_id": "Q01", "query": "..."}, ...]}, oppure una lista di oggetti o di stringhe
    .jsonl un oggetto {"query_id", "query"} per riga
    .csv colonna query_id più query (o question)
    .txt o altro una domanda per riga, facoltativamente Q01<TAB>testo della domanda

    Il campo del testo può chiamarsi query, question o text; l'identificativo query_id o id (cli.py:784-788). Gli identificativi contano: la valutazione unisce risultati e gold per query_id; senza, ripiega sul testo della domanda, che è fragile, e il CLI lo dice con un avviso (cli.py:968-977); se solo alcune domande lo hanno, l'avviso dice declares query_id for only N/M questions e le altre ripiegano sul testo (:977-983). Identificativi ripetuti fanno fallire il caricamento (:960-966).

    I gold set stanno in evaluation/gold/: gold_v3.json (inglese, quello dei driver), gold_v3_it.json (italiano), gold_circular_v1.json (congelato, con l'impronta in gold_circular_v1.sha256). Dettagli in Valutazione.

    Cosa viene salvato¶

    In <output-dir>/<data>_<ora>_<tag>/:

    file contenuto
    results.jsonl una riga per risposta (domanda × strategia): risposta, latenza, prove recuperate (contexts, retrieved_triples, retrieved_entities, retrieved_text_sources), contatori per canale, insufficient_answer, la risposta prima del tentativo di recupero dei rifiuti, metadata con modello e opzioni (runner.py:42-77)
    results.csv gli stessi dati in tabella
    summary.txt, summary.json per strategia: latenza media, triple e vicini medi, risposte "insufficienti" (runner.py:399-450); numero di domande e quante hanno query_id
    config.json gli argomenti del CLI, il grafo letto (NEO4J_URL, database, encoder; mai la password) e la configurazione completa di ogni strategia (cli.py:1073-1097). È il file da leggere per sapere con cosa è stato fatto un run, invece di fidarsi della storia della shell

    Due cose da sapere sul salvataggio

    • Si scrive tutto alla fine. Le risposte restano in memoria finché non sono finite tutte le domande di tutte le strategie (runner.py:92-175, cli.py:1030-1138): se il processo muore, non resta niente. Durante il run si vede solo una riga di log per domanda: [<strategia>] q<n>/<totale> latency_ms=… insufficient=… kg_triples=… (runner.py:163-171).
    • L'ora nel nome della cartella è quella di fine, non di inizio (cli.py:1062, calcolata dopo il ciclo).

    config.json contiene graph_target nei run lanciati con questo codice (cli.py:1083). I run salvati senza il campo, come l'esempio qui sotto, non registrano il grafo letto.

    Esempio reale¶

    /srv/projects/graphllm/experiments/exp_results_fixed_abstention/a1_repaired_prompt/20260818_024642_abst_a1_repaired_prompt/: 30 domande tutte con query_id, 8 strategie, results.jsonl di 3,9 MB. Configurazione registrata: Qwen/Qwen2.5-32B-Instruct-AWQ su :8000, tfidf, text_docs_dir=artifacts/corpus_circular22, max_new_tokens=1024. Latenza media per risposta, in secondi:

    default hybrid text_only no_retrieval text_plus_triples neighbors_focus subgraph_2hop shortest_path
    9,9 19,0 13,4 6,9 6,9 5,9 6,4 5,8

    Somma 74,1 secondi per domanda su tutte le strategie, quindi circa 37 minuti per 30 domande: coerente con i 37 minuti tra la fine del braccio A1 e quella di A2.

    Regole per confrontare i run¶

    • Stessa sessione del server, stesso stato del grafo. Tra sessioni diverse i numeri oscillano di circa ±0,03 (run_abstention_arms.sh:14-15): una differenza più piccola non è un risultato. Per questo i tre bracci di astensione e il braccio italiano vanno lanciati di seguito, senza riavviare il generatore.
    • Le famiglie di risultati non si mescolano. Ogni cartella exp_results_* è una famiglia con condizioni proprie (grafo, modello, canale testuale): righe di famiglie diverse non vanno nella stessa tabella. run_gold_variant.sh:8-10 lo dice per exp_results/ (Aura). Le famiglie sono descritte in Dove stanno i dati.
    • Non cambiare graphrag.config o graphrag.strategies per far fare una cosa diversa a un esperimento: sono ciò con cui sono state misurate le campagne, e i run futuri non sarebbero più confrontabili (AGENTS.md, Anti-patterns). Si cambia con un'opzione del CLI, in un braccio nuovo.
    • Mai GRAPHRAG_VECTOR_ALLOW_DEGRADED=1 in una campagna. Senza encoder il recupero deve fallire, non passare in silenzio al solo canale lessicale (.env.example).

    Come capire che ha funzionato¶

    Il log finisce con Experiment completed. Output directory: … seguito dal riepilogo (cli.py:1140-1143); i driver aggiungono === … done : <data> ===. Poi:

    python3 -c "import json;s=json.load(open('<cartella>/summary.json'));print(s['questions_count'],s['questions_with_query_id'],s['strategies'])"

    Deve dire 30 domande, 30 con query_id, le 8 strategie.

    Se qualcosa va storto¶

    sintomo causa rimedio
    generator not answering at http://localhost:8001/v1 generatore spento o su un'altra porta Servire i modelli; oppure BASE_URL=…
    vector index unusable; rebuild with scripts/kg/kg_vector_index.py l'indice vettoriale non punta più al grafo ricostruirlo: Ricostruire il grafo
    missing evaluation/gold/gold_v3_it.json manca il gold italiano scripts/gold/build_gold_it.py (run_italian_arm.sh:34)
    avviso declares no query_id file di domande senza identificativi usare un gold .json, o righe Q01<TAB>domanda
    avviso declares query_id for only N/M questions solo alcune domande hanno l'identificativo dare l'identificativo a tutte
    il processo muore a metà nessun salvataggio intermedio rilanciare; per lunghe campagne usare setsid nohup o il cluster
    numeri diversi da quelli di un vecchio run "a parità di tutto" famiglia, sessione del server o stato del grafo diversi confrontare i config.json; restare dentro una famiglia
