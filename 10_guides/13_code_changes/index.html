    Modificare il codice¶

    Quando serve¶

    Prima e dopo ogni modifica al codice: quali regole segue la repo, quali controlli lanciare, cosa controlla la CI su GitHub.

    Le regole del codice¶

    Da AGENTS.md, sezioni Code conventions (righe 203-216) e Anti-patterns (218-249):

    • tipi sempre, unioni con |; docstring in stile Google; logger graphrag o kg_pipeline; import nell'ordine libreria standard → terze parti → locali;
    • Cypher sempre con parametri, mai stringhe composte con l'input; scritture in blocco con UNWIND + MERGE, mai una query per giro di ciclo;
    • i commenti spiegano perché, al presente, senza storia (niente date, incidenti, misure, riferimenti ad audit o piani: vanno nel messaggio di commit);
    • niente except: nudo o except Exception: silenzioso;
    • i prompt stanno solo in PromptLibrary (src/graphrag/llm/prompts.py); le strategie di recupero solo in strategies.py (AGENTS.md:157-160);
    • il comportamento della demo si cambia in product/config.py, non in graphrag.config o graphrag.strategies: quelli sono le impostazioni con cui sono state misurate le campagne (AGENTS.md:242-243);
    • una chiave restituita da un nodo dell'agente e non dichiarata in RAGState (src/graphrag/types.py) sparisce senza errore (AGENTS.md:172-173, 197-199);
    • non aggiungere frasi generiche a _REFUSAL_MARKERS / _INSUFFICIENT_MARKERS (src/graphrag/llm/refusal.py): sono cercate come sottostringhe in tutta la risposta e alimentano sia la sostituzione della risposta sia una metrica pubblicata (AGENTS.md:233-235);
    • cambiare PromptLibrary.DEFAULT_DOMAIN_SCOPE o le frasi del filtro di dominio richiede di rilanciare le tre suite scripts/domain_gate/eval_domain_gate_llm.py, eval_domain_gate_heldout.py, eval_domain_gate_entities.py (AGENTS.md:237-239).

    Test che fissano comportamenti¶

    • tests/test_audit_fixes.py: 34 test, uno per ogni rilievo dell'audit del codice (AGENTS.md:295-298; contati 34 def test_). Se una modifica ne fa fallire uno, si è reintrodotto un difetto documentato.

    • tests/test_profiles.py e tests/test_profiles_match_runners.py: bloccano il profilo thesis_campaign sia contro la configurazione registrata da una campagna vera sia contro quella che i runner producono oggi. Vanno lanciati quando si tocca graphrag.profiles o le opzioni di un runner in scripts/runners/ (AGENTS.md:244-248).

    • tests/test_profile_prima.py: 8 test (contati 8 def test_) sul profilo DEMO_PROFILE=prima di product/config.py: spegne in blocco gli interruttori nuovi della demo e una variabile impostata esplicitamente vince sul profilo (docstring del file; elenco degli interruttori in test_profile_prima.py:20-29). Vanno lanciati quando si tocca un interruttore DEMO_* di product/config.py o il campo corrispondente di AgentConfig. Gli interruttori sono descritti in Avviare e fermare la demo.

    I controlli¶

    Tutti dalla radice della repo, nell'ambiente graphllm, con PYTHONNOUSERSITE=1 (vedi Ambiente Python).

    cosa si è toccato controllo (CLAUDE.md:131-144)
    solo documentazione git diff --check -- '*.md', poi verificare che i link relativi funzionino
    logica Python lo script di smoke più vicino
    qualunque cosa in src/ o product/ ruff check src product
    CLI o pipeline il comando più piccolo che passa dal codice toccato
    recupero o punteggi pytest tests/ evaluation/tests/ -q
    codice degli esperimenti aprire una cartella di risultati recente e controllare che i nomi dei file corrispondano a quelli che leggono gli script di analisi

    Suite completa¶

    CUDA_VISIBLE_DEVICES="" PYTHONNOUSERSITE=1 python -m pytest -q

    I percorsi dei test vengono da pyproject.toml (testpaths = ["tests", "kg_pipeline/tests", "evaluation/tests"], righe 114-119), quindi pytest funziona da qualunque cartella.

    Lint¶

    ruff check src product

    Misurato con ~/.local/bin/ruff check --no-cache src product: All checks passed!. Regole E4, E7, E9, F (pyproject.toml:131-137); scripts/, evaluation/ e kg_pipeline/ sono esclusi di proposito (commento a pyproject.toml:123-127).

    ruff non è nell'ambiente graphllm

    ruff è nell'extra dev (pyproject.toml:74-78), ma non era installato nell'ambiente conda (python -m ruff con PYTHONNOUSERSITE=1: No module named ruff). L'unico ruff sul server è ~/.local/bin/ruff (versione 0.15.13), nella cartella personale di Francesco. Per averlo: pip install -e ".[dev]" nell'ambiente.

    Sintassi con Python 3.10¶

    La CI controlla che il codice si compili con Python 3.10, la versione minima dichiarata:

    /usr/bin/python3.10 -m compileall -q src scripts kg_pipeline evaluation product

    Misurato: uscita 0. Poi, senza scrivere file compilati, ast.parse con /usr/bin/python3.10 su tutti i .py di quelle cartelle: 0 errori di sintassi.

    Smoke¶

    Misurati con la demo accesa (generatore su :8001, encoder su :8002):

    # le NEO4J_* del grafo di produzione, lette come dati, come fa start_demo.sh:55-60
while IFS='=' read -r k v; do [[ "$k" =~ ^NEO4J_[A-Z_]+$ ]] && export "$k=$v"; done < ~/.config/graphrag/graph-db.env

python scripts/smoke/smoke_check.py --llm-base-url http://localhost:8001/v1
python scripts/smoke/smoke_kg_retriever.py
python scripts/smoke/smoke_text_rag.py docs/ --query "Summarize the cluster setup" --top-k 4
CUDA_VISIBLE_DEVICES=1 python scripts/smoke/smoke_dense_rag.py docs/
    script cosa controlla esito
    smoke_check.py grafo raggiungibile con gli indici attivi, generatore, encoder SMOKE CHECK PASSED: 23250 nodes (+23250 :NodeVec carriers), indexes online, RedHatAI/Qwen3.8-27B-INT4, intfloat/multilingual-e5-base (eseguito con le NEO4J_* del grafo di produzione e --llm-base-url http://localhost:8001/v1; i nodi d'appoggio :NodeVec sono contati a parte, smoke_check.py:63-69, 88)
    smoke_kg_retriever.py il recupero dal grafo esportato KG RETRIEVER SMOKE PASSED
    smoke_text_rag.py recupero testuale su una cartella TEXT RAG SMOKE PASSED
    smoke_dense_rag.py recupero denso, domande in inglese e italiano, ricarica della cache DENSE RAG SMOKE PASSED

    smoke_check.py --env-file ~/.config/graphrag/graph-db.env invece fallisce con generator: base URL not configured e encoder: base URL not configured: quel file ha solo le NEO4J_*, e con un --env-file diverso lo script non legge kg_pipeline/.env, dove stanno gli indirizzi dei modelli. Il modo che funziona è quello del preflight della demo, sopra (start_demo.sh:186-191). Le opzioni dello script: --env-file, --check-imports-only, --skip-neo4j, --skip-llm, --skip-encoder, --llm-base-url (ripetibile), --llm-model, --timeout-sec (default 5).

    La CI su GitHub¶

    .github/workflows/ci.yml parte a ogni push su main o master e a ogni pull request. Tre lavori:

    lavoro cosa fa
    syntax Python 3.10, python -m compileall -q src scripts kg_pipeline evaluation product
    test Python 3.12, torch solo CPU, pip install -e ".[dev]", controllo che graphrag.__version__ coincida con la versione del pacchetto graphrag-pipeline, poi python -m pytest -q
    lint Python 3.12, solo ruff (>=0.6,<1.0), ruff check src product

    Il lavoro test installa solo da pyproject.toml, non dai file requirements*.txt: una dipendenza che sta solo lì fa fallire la CI (commento in ci.yml).
